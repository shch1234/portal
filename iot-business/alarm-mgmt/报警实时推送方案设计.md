# 报警实时推送方案设计

## 📋 问题分析

### 当前方案的问题

**现状**：报警数量统计接口采用传统的HTTP请求-响应模式
- ❌ 前端需要定时轮询（每10秒刷新）才能获取最新数据
- ❌ 报警发生后，前端无法立即感知，存在延迟（最多10秒）
- ❌ 浪费网络资源：即使数据未变化，也要定时请求
- ❌ 用户体验差：报警发生时，用户无法第一时间看到

### 业务需求

根据《物联网平台业务需求说明书》：
- **实时性要求**：10秒刷新（当前通过轮询实现）
- **业务场景**：报警数量变化需要及时通知用户
- **用户交互**：点击后查看详细列表

## 🔍 业界方案分析

### 方案对比

| 方案 | 实时性 | 实现复杂度 | 服务器资源 | 适用场景 | 推荐度 |
|------|--------|------------|------------|----------|--------|
| **HTTP轮询** | ⭐⭐ | ⭐⭐⭐⭐⭐ | ⭐⭐⭐ | 实时性要求低 | ❌ 不推荐 |
| **长轮询** | ⭐⭐⭐ | ⭐⭐⭐ | ⭐⭐ | 中等实时性 | ⭐⭐⭐ |
| **WebSocket** | ⭐⭐⭐⭐⭐ | ⭐⭐⭐ | ⭐⭐ | 高实时性、双向通信 | ⭐⭐⭐⭐⭐ |
| **SSE** | ⭐⭐⭐⭐ | ⭐⭐⭐⭐ | ⭐⭐⭐ | 高实时性、单向推送 | ⭐⭐⭐⭐ |
| **WebSocket + 消息队列** | ⭐⭐⭐⭐⭐ | ⭐⭐ | ⭐ | 大规模、高并发 | ⭐⭐⭐⭐ |

### 详细分析

#### 1. HTTP轮询（当前方案）

```javascript
// 前端实现
setInterval(() => {
    fetch('/api/v1/alarm/statistics/current-count')
        .then(res => res.json())
        .then(data => updateUI(data));
}, 10000); // 每10秒轮询
```

**优点**：
- ✅ 实现简单，无需额外技术栈
- ✅ 兼容性好，所有浏览器都支持

**缺点**：
- ❌ 延迟高：最多延迟10秒
- ❌ 资源浪费：无变化也要请求
- ❌ 无法及时响应：报警发生后不能立即感知

#### 2. 长轮询（Long Polling）

```javascript
// 前端实现
function longPolling() {
    fetch('/api/v1/alarm/statistics/current-count?timeout=30000')
        .then(res => res.json())
        .then(data => {
            updateUI(data);
            longPolling(); // 继续下一次长轮询
        });
}
```

**优点**：
- ✅ 相对实时：服务器可以立即响应变化
- ✅ 减少请求次数：相比短轮询

**缺点**：
- ❌ 服务器资源占用：需要保持连接
- ❌ 实现复杂：需要管理超时和重连
- ❌ HTTP连接数限制

#### 3. WebSocket（推荐方案⭐）

```javascript
// 前端实现
const ws = new WebSocket('ws://localhost:8080/api/v1/alarm/ws');
ws.onmessage = (event) => {
    const data = JSON.parse(event.data);
    if (data.type === 'ALARM_COUNT_CHANGED') {
        updateUI(data.payload);
    }
};
```

**优点**：
- ✅ 实时性好：服务器主动推送，毫秒级延迟
- ✅ 双向通信：可以发送控制指令
- ✅ 资源效率：单连接复用
- ✅ 标准协议：浏览器原生支持

**缺点**：
- ⚠️ 需要维护连接状态
- ⚠️ 需要处理断线重连
- ⚠️ 负载均衡需要粘性会话（Sticky Session）

#### 4. Server-Sent Events (SSE)（备选方案）

```javascript
// 前端实现
const eventSource = new EventSource('/api/v1/alarm/statistics/stream');
eventSource.onmessage = (event) => {
    const data = JSON.parse(event.data);
    updateUI(data);
};
```

**优点**：
- ✅ 实时性好：服务器主动推送
- ✅ 自动重连：浏览器自动处理
- ✅ 实现简单：比WebSocket更简单
- ✅ 单向推送：适合通知场景

**缺点**：
- ❌ 只支持单向通信（服务器→客户端）
- ❌ 部分老浏览器不支持（IE不支持）

#### 5. WebSocket + 消息队列（大规模场景）

**架构**：
```
TB报警 → Webhook → Portal后端 → Kafka/RabbitMQ → WebSocket推送 → 前端
```

**优点**：
- ✅ 解耦：后端通过消息队列通知
- ✅ 可扩展：支持多个WebSocket服务实例
- ✅ 高可用：消息队列保证消息不丢失

**缺点**：
- ❌ 架构复杂：需要引入消息队列
- ❌ 运维成本高：需要维护消息队列

## 🎯 推荐方案

### 方案一：WebSocket实时推送（推荐⭐⭐⭐⭐⭐）

**适用场景**：当前阶段，报警数量实时性要求高

**架构设计**：

```
┌─────────────┐     ┌──────────────┐     ┌─────────────┐
│ ThingsBoard │────▶│ Portal后端   │────▶│ WebSocket   │
│ 报警触发     │     │ 更新数据库    │     │ 推送给前端   │
└─────────────┘     └──────────────┘     └─────────────┘
                            │
                            ▼
                    ┌──────────────┐
                    │ PostgreSQL   │
                    │ alarm_history│
                    └──────────────┘
```

**实现要点**：

1. **后端WebSocket服务**
   - 连接管理：维护客户端连接列表
   - 房间（Room）机制：按工厂/车间分组推送
   - 消息推送：报警数量变化时主动推送

2. **数据更新触发**
   - Webhook接收报警数据后，更新数据库
   - 同时触发WebSocket推送

3. **前端连接**
   - 建立WebSocket连接
   - 订阅特定工厂/车间的报警数量
   - 接收推送后更新UI

**优点**：
- ✅ 实时性好：毫秒级延迟
- ✅ 用户体验佳：报警发生立即看到
- ✅ 资源效率：单连接复用
- ✅ 扩展性强：后续可以推送更多实时数据

### 方案二：SSE实时推送（备选⭐⭐⭐⭐）

**适用场景**：如果只需要单向推送，不需要双向通信

**实现要点**：
- 后端实现SSE端点：`/api/v1/alarm/statistics/stream`
- 前端使用EventSource接收推送
- 报警数据更新时，通过SSE推送

**优点**：
- ✅ 实现比WebSocket更简单
- ✅ 自动重连机制
- ✅ 适合纯推送场景

### 方案三：混合方案（渐进式升级⭐⭐⭐⭐⭐）

**第一阶段**：保持现有HTTP接口，前端使用短轮询
- 快速上线，稳定可靠

**第二阶段**：引入WebSocket，前端渐进式升级
- 支持WebSocket的浏览器使用实时推送
- 不支持的回退到轮询

**第三阶段**：完全切换到WebSocket
- 所有客户端使用实时推送
- 保留HTTP接口作为降级方案

### 1. 后端实现

#### 1.1 WebSocket配置

```java
@Configuration
@EnableWebSocket
public class WebSocketConfig implements WebSocketConfigurer {
    
    @Override
    public void registerWebSocketHandlers(WebSocketHandlerRegistry registry) {
        registry.addHandler(new AlarmStatisticsWebSocketHandler(), "/api/v1/alarm/ws")
                .setAllowedOrigins("*"); // 生产环境应配置具体域名
    }
}
```

#### 1.2 WebSocket处理器

```java
@Component
public class AlarmStatisticsWebSocketHandler extends TextWebSocketHandler {
    
    // 按订阅信息分组管理连接
    private final Map<String, Set<WebSocketSession>> subscriptions = new ConcurrentHashMap<>();
    
    @Override
    public void afterConnectionEstablished(WebSocketSession session) {
        // 解析订阅信息（工厂ID、车间ID等）
        String subscriptionKey = getSubscriptionKey(session);
        subscriptions.computeIfAbsent(subscriptionKey, k -> ConcurrentHashMap.newKeySet())
                    .add(session);
    }
    
    /**
     * 推送报警数量变化
     */
    public void pushAlarmCountChanged(String tenantId, String factoryId, String workshopId, 
                                     CurrentAlarmDeviceCountVO count) {
        String subscriptionKey = buildSubscriptionKey(tenantId, factoryId, workshopId);
        Set<WebSocketSession> sessions = subscriptions.get(subscriptionKey);
        if (sessions != null) {
            String message = JSON.toJSONString(Map.of(
                "type", "ALARM_COUNT_CHANGED",
                "payload", count
            ));
            sessions.forEach(session -> {
                try {
                    session.sendMessage(new TextMessage(message));
                } catch (IOException e) {
                    log.error("推送消息失败", e);
                }
            });
        }
    }
}
```

#### 1.3 报警服务集成

```java
@Service
@RequiredArgsConstructor
public class AlarmStatisticsServiceImpl implements AlarmStatisticsService {
    
    private final AlarmStatisticsRepository repository;
    private final AlarmStatisticsWebSocketHandler webSocketHandler; // 注入WebSocket处理器
    
    @Override
    public void receiveAlarmWebhook(String tenantId, AlarmWebhookRequest request) {
        // 1. 更新数据库
        AlarmHistoryDO alarm = saveOrUpdateAlarm(tenantId, request);
        
        // 2. 查询更新后的统计
        CurrentAlarmDeviceCountVO count = getCurrentAlarmDeviceCount(
            tenantId, alarm.getFactoryId(), alarm.getWorkshopId());
        
        // 3. 推送给订阅的客户端
        webSocketHandler.pushAlarmCountChanged(
            tenantId, alarm.getFactoryId(), alarm.getWorkshopId(), count);
    }
}
```

### 2. 前端实现

```javascript
// WebSocket连接管理
class AlarmStatisticsWS {
    constructor(tenantId, factoryId, workshopId) {
        this.tenantId = tenantId;
        this.factoryId = factoryId;
        this.workshopId = workshopId;
        this.ws = null;
    }
    
    connect() {
        const wsUrl = `ws://localhost:8080/api/v1/alarm/ws?tenantId=${this.tenantId}&factoryId=${this.factoryId}&workshopId=${this.workshopId}`;
        this.ws = new WebSocket(wsUrl);
        
        this.ws.onopen = () => {
            console.log('WebSocket连接已建立');
            // 订阅报警数量变化
            this.subscribe();
        };
        
        this.ws.onmessage = (event) => {
            const data = JSON.parse(event.data);
            if (data.type === 'ALARM_COUNT_CHANGED') {
                this.onAlarmCountChanged(data.payload);
            }
        };
        
        this.ws.onerror = (error) => {
            console.error('WebSocket错误', error);
        };
        
        this.ws.onclose = () => {
            console.log('WebSocket连接已关闭');
            // 5秒后重连
            setTimeout(() => this.connect(), 5000);
        };
    }
    
    subscribe() {
        this.ws.send(JSON.stringify({
            type: 'SUBSCRIBE',
            tenantId: this.tenantId,
            factoryId: this.factoryId,
            workshopId: this.workshopId
        }));
    }
    
    onAlarmCountChanged(count) {
        // 更新UI
        updateAlarmCountUI(count);
    }
    
    disconnect() {
        if (this.ws) {
            this.ws.close();
        }
    }
}

// 使用
const alarmWS = new AlarmStatisticsWS(tenantId, factoryId, workshopId);
alarmWS.connect();
```

## 📊 方案对比总结

### 性能对比

| 指标 | HTTP轮询 | 长轮询 | WebSocket | SSE |
|------|----------|--------|-----------|-----|
| 延迟 | 0-10秒 | 0-30秒 | <100ms | <100ms |
| 服务器连接数 | 低 | 中 | 中 | 中 |
| 带宽消耗 | 高 | 中 | 低 | 低 |
| 实时性 | ⭐⭐ | ⭐⭐⭐ | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐ |

### 实施建议

1. **短期**（当前阶段）：
   - 保持HTTP轮询作为基础方案
   - 开始设计WebSocket方案

2. **中期**（1-2周）：
   - 实现WebSocket实时推送
   - 前端渐进式升级，支持两种方式并存

3. **长期**（未来扩展）：
   - 完全切换到WebSocket
   - 扩展到其他实时数据推送（设备状态、指标等）

## 🎯 最终推荐

**推荐方案：WebSocket实时推送 + HTTP轮询降级**

**理由**：
1. ✅ 实时性好：毫秒级延迟，报警发生立即推送
2. ✅ 用户体验佳：无需手动刷新，自动更新
3. ✅ 资源效率：单连接复用，比轮询更节省资源
4. ✅ 可扩展：后续可以推送更多实时数据（设备状态、指标等）
5. ✅ 有降级方案：不支持WebSocket时自动降级到轮询
