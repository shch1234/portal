# 当前报警设备统计接口实现说明

## 1. 业务需求

根据《物联网平台业务需求说明书》4.3.1节：

- **当前报警设备数量**：统计车间内所有正在报警的设备个数
- **重要提示**：一台设备可能有多个报警，但只统计设备个数（去重）
- **交互**：用户点击后可以筛选正在报警的设备列表
- **实时性**：10秒刷新

## 2. 接口设计

### 2.1 获取当前报警设备数量

**接口路径**：`GET /api/v1/alarm/statistics/current-count`

**请求参数**：
- `tenantId`（必填）：租户ID
- `factoryId`（必填）：工厂ID
- `workshopId`（可选）：车间ID，如果不填则查询该工厂下所有车间的报警设备

**响应示例**：
```json
{
  "code": 200,
  "message": "成功",
  "data": {
    "factoryId": "factory-1",
    "factoryName": "增速器厂区",
    "workshopId": "workshop-1",
    "workshopName": "CNC车间",
    "deviceCount": 5
  }
}
```

### 2.2 查询当前报警设备列表

**接口路径**：`POST /api/v1/alarm/statistics/current-devices`

**请求参数**：
- `tenantId`（必填，Query参数）：租户ID
- `request`（Body）：
  ```json
  {
    "factoryId": "factory-1",
    "workshopId": "workshop-1",
    "pageNo": 1,
    "pageSize": 10
  }
  ```

**响应示例**：
```json
{
  "code": 200,
  "message": "成功",
  "data": {
    "records": [
      {
        "deviceId": "device-1",
        "deviceCode": "CNC001",
        "deviceName": "五轴加工中心01",
        "deviceType": "机床",
        "deviceSubType": "五轴铣车中心",
        "workshopName": "CNC车间",
        "alarmCount": 2,
        "latestAlarmStartTs": 1705678900000
      }
    ],
    "total": 5
  }
}
```

### 3.2 数据查询逻辑

#### 3.2.1 当前报警设备数量查询

**SQL核心逻辑**：
```sql
SELECT DISTINCT
    dbi.id AS deviceId,
    dbi.device_code AS deviceCode,
    dbi.device_name AS deviceName,
    -- ... 其他字段
    COUNT(ah.id) AS alarmCount,
    MAX(ah.start_ts) AS latestAlarmStartTs
FROM biz_device_mgmt.alarm_history ah
INNER JOIN biz_device_base.device_base_info dbi ON ah.device_id = dbi.id
WHERE ah.tenant_id = :tenantId
  AND ah.is_active = true
  AND dbi.factory_id = :factoryId
  AND dbi.workshop_id = :workshopId  -- 可选
GROUP BY dbi.id, dbi.device_code, ...
ORDER BY latestAlarmStartTs DESC
```

**关键点**：
- ✅ 使用 `DISTINCT` + `GROUP BY` 确保设备ID去重
- ✅ 只查询 `is_active = true` 的报警记录
- ✅ 通过 `JOIN` 设备基础信息表获取车间信息
- ✅ 统计每个设备的报警数量

#### 3.2.2 分页查询

使用MyBatis的 `LIMIT` 和 `OFFSET` 实现分页：
- 总数查询：`COUNT(DISTINCT dbi.id)`
- 分页查询：`LIMIT :limit OFFSET :offset`

- ✅ `workshop_id`：车间隔离（可选）

## 6. 性能优化

### 6.1 索引利用

查询利用了以下索引：
- `idx_alarm_history_active`：`(device_id, is_active) WHERE is_active = true`
- `idx_alarm_history_tenant`：`tenant_id`
- `device_base_info` 表的相关索引：`factory_id`, `workshop_id`

### 6.2 查询优化

- ✅ 使用 `DISTINCT` + `GROUP BY` 在数据库层去重，减少数据传输
- ✅ 只查询必要的字段，避免 `SELECT *`
- ✅ 按最新报警时间排序，优先展示最紧急的设备

## 7. 扩展性考虑

### 7.1 未来可能的扩展

1. **按报警级别统计**：区分不同级别的报警（INFO/WARNING/ERROR/CRITICAL）
2. **实时推送**：使用WebSocket推送报警设备数量变化

4. **聚合统计**：支持按时间范围、按设备类型等维度聚合统计

### 7.2 预留接口

当前接口设计考虑了未来扩展：
- 查询请求中的 `workshopId` 是可选的，可以扩展为支持多车间查询
- 响应结构支持扩展字段（如报警级别统计）

## 8. 注意事项

### 8.1 数据一致性

- 报警数据的 `is_active` 字段必须及时更新（报警结束时设为 `false`）
- 设备与车间的关系变更时，统计结果会自动反映（因为使用JOIN查询）

### 8.2 性能考虑

- 对于设备数量较多的场景，建议：
  - 按车间查询，避免全厂查询
  - 适当使用缓存（注意缓存失效策略）
  - 监控慢查询，必要时优化SQL

### 8.3 实时性

- 当前实现每次请求都查询数据库，保证数据实时性
- 如果未来需要更高的性能，可以考虑：
  - 使用Redis缓存统计结果（10秒刷新）
  - 使用消息队列异步更新缓存
