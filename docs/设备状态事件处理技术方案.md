# 设备状态事件处理技术方案

**文档版本**：v1.0  
**创建日期**：2025-12-08  
**最后更新**：2025-12-08

---

## 📋 文档说明

本文档详细描述了Portal端处理ThingsBoard发送的设备状态事件（DeviceStateEvent）的技术方案，包括正常状态转换、异常情况处理、数据修复机制等核心逻辑。

**适用场景**：
- 实时状态甘特图数据生成
- 设备状态时间线记录
- 状态转换异常检测与修复

---

## 🎯 业务需求

### 1. 事件数据结构

ThingsBoard发送的DeviceStateEvent包含以下关键信息：
- `previousState`：上一个设备状态（如：WORKING、STANDBY、FAULT等）
- `currentState`：当前设备状态（如：STANDBY、FAULT、SHUTDOWN等）
- `timestamp`：事件时间戳（秒，Unix时间戳）
- `dataTimestamp`：数据时间戳（设备实际时间，可选）

### 2. 核心业务目标

1. **状态时间线完整性**：保证设备状态时间线连续、无间隙
2. **状态转换准确性**：准确记录状态转换时间点
3. **异常检测与修复**：及时发现并修复状态不匹配问题
4. **数据可追溯性**：记录异常情况，便于后续分析和修复

---

## 📊 数据表结构

### device_state_record 表

| 字段名 | 类型 | 说明 |
|--------|------|------|
| id | BIGINT | 主键ID（雪花算法） |
| tenant_uuid | CHAR(36) | 租户UUID |
| device_info_id | BIGINT | 设备ID |
| org_factory_id | BIGINT | 所属厂区ID（冗余字段，优化查询性能） |
| state_code | VARCHAR(50) | 状态编码（WORKING/STANDBY/FAULT/SHUTDOWN等） |
| start_ts | BIGINT | 状态开始时间戳（秒） |
| end_ts | BIGINT | 状态结束时间戳（秒，NULL表示进行中） |
| duration_s | INT | 持续时长（秒） |
| shift_date | DATE | 所属班次日期 |
| shift_code | VARCHAR(50) | 班次编码 |
| properties | JSON | 扩展属性 |
| is_complete | TINYINT(1) | 是否完整片段（1-完整，0-跨班切分或数据缺失） |

**关键索引**：
- `idx_state_record_device`：`(device_info_id, start_ts)`
- `idx_state_record_open`：`(device_info_id, end_ts)` - 用于查询进行中的状态
- `idx_state_record_factory_time`：`(org_factory_id, start_ts)` - 用于按工厂查询
- `idx_state_record_factory_shift`：`(org_factory_id, shift_date, shift_code)` - 用于按工厂和班次查询

## 🔄 处理流程

### 整体流程图

```
开始处理 DeviceStateEvent
    ↓
1. 数据准备阶段
    ├─ 解析事件：previousState, currentState, timestamp
    ├─ 查询设备信息（deviceCode → deviceInfoId）
    └─ 查询数据库最新状态记录（end_ts IS NULL 或最新的 end_ts）
    ↓
2. 状态匹配判断
    ├─ 情况A：首次连接（previousState = NULL）
    ├─ 情况B：正常匹配（DB最新状态 = previousState）
    ├─ 情况C：状态不匹配（异常情况）
    └─ 情况D：数据库无记录（首次记录）
    ↓
3. 异常处理策略（情况C）
    ├─ 子情况C1：数据库状态已结束（end_ts IS NOT NULL）
    ├─ 子情况C2：数据库状态进行中（end_ts IS NULL）
    └─ 子情况C3：时间戳异常（事件时间 < 数据库状态开始时间）
    ↓
4. 数据更新与插入
    ├─ 更新旧状态记录（设置 end_ts、duration_s）
    ├─ 插入新状态记录
    └─ 记录异常日志（如需要）
    ↓
结束
```

## 📝 详细处理逻辑

### 情况A：首次连接（previousState = NULL）

**场景**：设备首次连接，TB发送的状态事件中 previousState 为 NULL。

**处理逻辑**：
1. 直接插入新状态记录
2. 字段设置：
   - `state_code` = currentState
   - `start_ts` = 事件时间戳（优先使用 dataTimestamp，否则使用 timestamp）
   - `end_ts` = NULL（进行中）
   - `duration_s` = NULL（进行中）
   - `is_complete` = 1（完整记录）

**示例**：
```
事件：previousState = NULL, currentState = "STANDBY", timestamp = 1702008000
数据库：无记录
结果：插入一条新记录，state_code = "STANDBY", start_ts = 1702008000, end_ts = NULL
```

---

### 情况B：正常匹配（DB最新状态 = previousState）

**场景**：数据库中的最新状态与事件中的 previousState 匹配，这是正常的状态转换。

**处理逻辑**：
1. **更新数据库最新状态记录**：
   - `end_ts` = 事件时间戳（previousState 结束时间）
   - `duration_s` = end_ts - start_ts
   - `is_complete` = 1（完整记录）

2. **插入新状态记录**：
   - `state_code` = currentState
   - `start_ts` = 事件时间戳（currentState 开始时间）
   - `end_ts` = NULL（进行中）
   - `duration_s` = NULL（进行中）
   - `is_complete` = 1（完整记录）

**示例**：
```
事件：previousState = "WORKING", currentState = "STANDBY", timestamp = 1702008000
数据库最新记录：state_code = "WORKING", start_ts = 1702004400, end_ts = NULL

处理结果：
1. 更新数据库记录：end_ts = 1702008000, duration_s = 3600
2. 插入新记录：state_code = "STANDBY", start_ts = 1702008000, end_ts = NULL
```

---

### 情况C：状态不匹配（异常情况）

这是最复杂的情况，需要根据数据库状态的不同情况进行处理。

#### 子情况C1：数据库状态已结束（end_ts IS NOT NULL）

**场景**：数据库中的最新状态记录已经结束（end_ts IS NOT NULL），但事件中的 previousState 不匹配。

**可能原因**：
- 事件延迟到达（网络问题）
- 中间状态丢失（事件丢失）
- 设备重启后状态重置

**处理策略**：
1. **检查是否存在状态间隙**：
   - 如果 `数据库最新记录的 end_ts < 事件时间戳`，说明存在时间间隙
   - 插入 UNKNOWN 状态记录填充间隙：
     - `state_code` = "UNKNOWN"
     - `start_ts` = 数据库最新记录的 end_ts
     - `end_ts` = 事件时间戳
     - `duration_s` = end_ts - start_ts
     - `is_complete` = 0（标记为不完整，需要后续修复）
     - `properties` = `{"gap_reason": "状态不匹配导致间隙", "expected_previous": "WORKING", "actual_db_state": "STANDBY"}`

2. **插入新状态记录**（currentState）

3. **记录异常日志**：
   - 记录到 `webhook_fail_log` 表
   - 错误类型：`STATE_MISMATCH`
   - `need_manual = false`（可以自动修复）

**示例**：
```
事件：previousState = "WORKING", currentState = "STANDBY", timestamp = 1702008000
数据库最新记录：state_code = "STANDBY", start_ts = 1702004400, end_ts = 1702005000

处理结果：
1. 检测到间隙：1702005000 < 1702008000
2. 插入UNKNOWN记录：start_ts = 1702005000, end_ts = 1702008000
3. 插入新记录：state_code = "STANDBY", start_ts = 1702008000
```

---

#### 子情况C2：数据库状态进行中（end_ts IS NULL）

**场景**：数据库中的最新状态仍在进行中（end_ts IS NULL），但事件中的 previousState 不匹配。

**可能原因**：
- 状态丢失（中间状态未收到）
- 设备重启导致状态重置
- 网络问题导致事件乱序到达

**处理策略（推荐）**：

1. **将数据库中的进行中状态标记为 UNKNOWN**：
   - `state_code` = "UNKNOWN"
   - `end_ts` = 事件时间戳（或 previousState 应该结束的时间）
   - `duration_s` = end_ts - start_ts
   - `is_complete` = 0（标记为不完整，需要后续修复）
   - `properties` = `{"mismatch_reason": "previousState不匹配", "expected": "WORKING", "actual_db": "STANDBY", "event_previous": "FAULT"}`

2. **如果 previousState 不为 NULL**：
   - 插入 previousState 状态记录（用于修复时间线）
   - `state_code` = previousState
   - `start_ts` = 数据库 UNKNOWN 状态的 end_ts
   - `end_ts` = 事件时间戳
   - `duration_s` = end_ts - start_ts
   - `is_complete` = 0（标记为修复记录）
   - `properties` = `{"recovery": true, "recovered_from": "UNKNOWN"}`

3. **插入新状态记录**（currentState）

4. **记录异常日志**：
   - 记录到 `webhook_fail_log` 表
   - 错误类型：`STATE_MISMATCH`
   - `need_manual = true`（需要人工审核，因为可能存在数据丢失）

**示例**：
```
事件：previousState = "FAULT", currentState = "STANDBY", timestamp = 1702008000
数据库最新记录：state_code = "WORKING", start_ts = 1702004400, end_ts = NULL

处理结果：
1. 更新数据库记录：state_code = "UNKNOWN", end_ts = 1702008000, duration_s = 3600, is_complete = 0
2. 插入previousState记录：state_code = "FAULT", start_ts = 1702008000, end_ts = 1702008000, is_complete = 0
3. 插入新记录：state_code = "STANDBY", start_ts = 1702008000, end_ts = NULL
```

---

#### 子情况C3：时间戳异常（事件时间 < 数据库状态开始时间）

**场景**：事件时间戳早于数据库状态开始时间，导致时间倒流。

**可能原因**：
- 设备时钟不同步
- 事件严重延迟到达
- 事件乱序

**处理策略**：
1. **记录告警日志**：时间戳异常，可能存在时钟不同步
2. **使用数据库当前时间作为 start_ts**（避免时间倒流）
3. **插入新状态记录**：
   - `start_ts` = 数据库当前时间（NOW()）
   - `is_complete` = 0（标记为不完整）
   - `properties` = `{"timestamp_anomaly": true, "event_timestamp": 1702008000, "db_timestamp": 1702010000}`
4. **记录异常日志**：
   - 错误类型：`TIMESTAMP_ANOMALY`
   - `need_manual = true`（需要人工审核）

---

### 情况D：数据库无记录（首次记录）

**场景**：数据库中没有任何该设备的状态记录。

**处理逻辑**：
1. 直接插入新状态记录
2. 如果 previousState 不为 NULL，记录警告日志（理论上不应该发生）

**示例**：
```
事件：previousState = "WORKING", currentState = "STANDBY", timestamp = 1702008000
数据库：无记录

处理结果：
1. 插入新记录：state_code = "STANDBY", start_ts = 1702008000
2. 记录警告：previousState不为NULL但数据库无记录
```

## 🛡️ 异常处理最佳实践

### 1. UNKNOWN 状态的使用

**用途**：
- 填充状态间隙
- 标记异常状态
- 保证时间线连续性

**标记规则**：
- `is_complete = 0`：表示需要人工审核或自动修复
- `properties` 中记录异常原因和修复信息

**修复机制**：
- 提供修复接口，允许将 UNKNOWN 状态修正为实际状态
- 定期扫描 `is_complete = 0` 的记录，尝试自动修复
- 提供人工修复界面

---

### 2. 并发控制

**问题**：多事件并发处理可能导致状态不一致。

**解决方案**：
- **方案A：数据库行锁**
  ```sql
  SELECT * FROM device_state_record 
  WHERE device_info_id = ? AND (end_ts IS NULL OR end_ts = (SELECT MAX(end_ts) FROM device_state_record WHERE device_info_id = ?))
  FOR UPDATE
  ```

- **方案B：分布式锁（Redis）**
  ```java
  String lockKey = "device_state_lock:" + deviceInfoId;
  if (redisLock.tryLock(lockKey, 5, TimeUnit.SECONDS)) {
      try {
          // 处理状态更新
      } finally {
          redisLock.unlock(lockKey);
      }
  }
  ```

**推荐**：使用分布式锁，避免数据库锁导致的性能问题。

---

### 3. 时间戳处理策略

**优先级**：
1. 优先使用事件中的 `dataTimestamp`（设备实际时间）
2. 如果没有 `dataTimestamp`，使用 `timestamp`（事件接收时间）
3. 记录 `received_time`（Portal接收时间）用于对账

**时间戳验证**：
- 如果事件时间与数据库时间差距过大（如 > 1小时），记录告警
- 可能是时钟不同步或事件严重延迟

---

### 4. 异常日志记录

**记录内容**：
- 记录到 `webhook_fail_log` 表
- 错误类型：`STATE_MISMATCH` 或 `TIMESTAMP_ANOMALY`
- 详细信息：
  - 数据库状态：`state_code`, `start_ts`, `end_ts`
  - 事件状态：`previousState`, `currentState`, `timestamp`
  - 异常原因：`mismatch_reason`, `gap_reason` 等

**人工处理标记**：
- `need_manual = true`：需要人工审核的情况
- `need_manual = false`：可以自动修复的情况

---

### 5. 监控与告警

**监控指标**：
- 状态不匹配频率（按设备、按时间段统计）
- UNKNOWN 状态数量（按设备统计）
- 时间戳异常频率
- 状态转换延迟（事件时间戳 - 数据库时间戳）

**告警规则**：
- 单个设备状态不匹配频率 > 10次/小时：触发告警
- UNKNOWN 状态数量 > 100条：触发告警
- 时间戳异常频率 > 5次/小时：触发告警

---

### 6. 数据修复机制

**自动修复任务**：
- 定期扫描 `is_complete = 0` 的记录
- 尝试从其他数据源（如设备历史数据）修复状态
- 如果无法自动修复，标记为需要人工处理

**人工修复接口**：
- 提供管理界面，允许运维人员查看和修正状态
- 支持批量修复
- 记录修复历史

**对账任务**：
- 定期与 TB 数据对比，发现并修复差异
- 对比时间线完整性
- 发现缺失的状态记录

## 🔧 实现要点

### 1. Repository 扩展

需要在 `DeviceStateTimelineRepository` 中添加以下方法：

```java
/**
 * 查询设备最新的状态记录（进行中或最近结束的）
 */
Optional<DeviceStateTimelineDO> findLatestState(String tenantId, String deviceInfoId);

/**
 * 插入状态记录
 */
void insert(DeviceStateTimelineDO record);

/**
 * 更新状态记录
 */
void update(DeviceStateTimelineDO record);
```

### 2. 事务管理

**要求**：
- 更新旧记录和插入新记录应在同一事务中
- 保证数据一致性
- 使用 `@Transactional` 注解

### 3. 幂等性检查

**实现**：
- 基于 `messageId` 检查是否已处理
- 避免重复处理导致数据重复
- 使用 Redis 或数据库唯一索引

### 4. 状态转换验证（可选）

**实现**：
- 定义合法状态转换规则
- 非法转换记录告警，不直接插入
- 例如：WORKING → STANDBY 合法，WORKING → FAULT 需验证

---

## 📈 性能优化建议

### 1. 批量处理

- 对于批量状态更新，使用批量插入
- 减少数据库交互次数

### 2. 索引优化

- 确保 `(device_info_id, end_ts)` 索引存在
- 用于快速查询进行中的状态

### 3. 缓存策略

- 缓存设备最新状态（Redis）
- 减少数据库查询
- TTL = 60秒

### 4. 异步处理

- 状态更新操作可以异步处理
- 提高 Webhook 接收接口响应速度
